# Инструкции по разработке «Артикидс»

Эти инструкции относятся ко всему Flutter-проекту. Цель ближайшей версии — дать врачу назначить упражнение, ребёнку выполнить его с котом, который повторяет мимику в реальном времени, и сохранить подтверждённый результат вместе с наградой.

Перед изменениями прочитайте [план MVP](docs/MVP_PLAN.md). В нём описаны каталог упражнений, этапы, условия автоматической проверки звука и сценарий презентации. Учитывайте допущения плана при оценке задачи. Первое демонстрационное устройство — Android-телефон, роли работают локально на одном устройстве. Точные параметры упражнения выбирает специалист.

## Где начинать изменение

| Если задача касается | Сначала посмотрите |
| --- | --- |
| Входа, кота, списка или запуска занятия | `lib/main.dart`, `lib/widgets/task_tile.dart`, графику в `assets/` |
| Назначений врача и доступных ребёнку задач | `lib/pages/settings_page.dart`, `lib/pages/task_creator_page.dart`, `lib/services/task_service.dart` |
| Данных и совместимости | `lib/models/task.dart`, `lib/services/task_service.dart`, `assets/tasks.json`, `lib/pages/history_page.dart` |
| Нативных зависимостей и разрешений | `pubspec.yaml`, `android/app/build.gradle.kts`, `android/app/src/main/AndroidManifest.xml` |
| Проверок интерфейса | `test/widget_test.dart`. Исходный тест ожидает шаблонный счётчик. При первом изменении этого потока замените его тестом реального экрана с изолированным хранилищем. |

Сверяйтесь с текущим деревом и `git status --short`. В репозитории встречаются отслеживаемые сборочные файлы и локальные изменения. Работайте с исходниками в `lib/`, ресурсами и нужным платформенным кодом. Существование APK в `build/` само по себе не подтверждает работоспособность текущей версии.

## Правила реализации

- Сохраняйте путь пользователя через обычные экраны. Врач выбирает профиль, упражнение и параметры в режиме взрослого. Ребёнок открывает своё назначение. Статусы задания и основание зачёта должны одинаково читаться на домашнем экране и в истории.
- Отделите источник наблюдений от управления занятием и от отрисовки. Источник сообщает время, доступность и измеренные признаки. Кот использует эти признаки для непрерывной анимации. Контроллер сравнивает их с условиями назначения. Та же граница позволит подключить датчики маски. До появления устройства достаточно программного контракта и тестового источника.
- Для повтора проверяйте качество сигнала, заданное удержание и возврат в нейтраль перед следующим повтором. В комбинированном упражнении поза и целевой гласный должны совпасть по времени. Таймер может измерять длительность уже наблюдаемого действия. Истечение времени, громкость и нажатие «Начать» сами по себе не завершают упражнение.
- При низкой уверенности предложите повтор или подтверждение услышанного присутствующим врачом. Подтверждение доступно в режиме взрослого. Сохраняйте способ оценки. Различайте «услышан голос», «распознан целевой звук» и «подтвердил врач» в интерфейсе и данных. Автоматический зачёт для группы пользователей включайте после проверки из плана MVP.
- При потере лица или сигнала прерывайте текущее удержание. При выходе со страницы, сворачивании и отзыве разрешения освобождайте камеру, микрофон и подписки. Отбрасывайте запоздавшие события завершённой попытки. Обработайте повторное открытие, отмену и быстрый двойной тап.
- Обрабатывайте изображение и звук на устройстве. Для истории достаточно параметров назначения, итога и способа проверки. Исключите из файлов, аналитики и логов сырые кадры, аудио, координаты лица и содержимое детского профиля. В тестах используйте синтетические события и вымышленные профили.
- Меняя хранилище, проверьте установленную версию со старым `tasks.json` и чистую установку из `assets/tasks.json`. Сохраните ID или назначьте их один раз, перенесите дату, текст и прежние завершения. Ошибка импорта должна быть видна взрослому и допускать повтор. Прежнюю задачу со свободным названием связывает с упражнением врач.
- Записывайте завершение и награду атомарно с уникальным ключом назначения. При ошибке сохранения оставьте возможность повторить запись. Показывайте полученные рыбки после успешной операции. Проверяйте баланс, историю и выбранную внешность после полного перезапуска процесса.
- Пишите детские команды по-русски, предлагайте одно действие за раз. Оставляйте доступными пример, паузу и выход. По потере сигнала подскажите, что можно сделать. Повторная попытка сохраняет уже заработанные рыбки. Новая внешность кота должна поддерживать те же движения, что и базовая.

## Как вести задачу

1. Найдите в плане пользовательский результат текущего этапа. До правки укажите, какое наблюдаемое действие должно сработать и какой близкий пример должен оставить счётчик без изменения.
2. Начните с участка, который снимает неопределённость. Для распознавания это проверка на целевом телефоне, для хранения — воспроизводимый пример со старыми данными. Используйте существующие страницы и сервисы, выносите новое поведение из виджетов по мере появления логики.
3. Внесите минимальное сквозное изменение. При подключении модели проверьте поддержку устройства и работу без сети, зафиксируйте версию зависимости и ресурс модели. Добавьте тест на конкретное правило, ошибку или миграцию, которую может нарушить изменение.
4. Для изменений Dart отформатируйте затронутые файлы. Из корня проекта используйте следующие команды по назначению.

   | Проверка | Команда |
   | --- | --- |
   | Получить зависимости при подготовке среды или изменении пакетов | `flutter pub get` |
   | Проверить статический анализ и тесты | `flutter analyze`, затем `flutter test` |
   | Найти телефон и открыть приложение | `flutter devices`, затем `flutter run -d <deviceId>` |
   | Подготовить и проверить сборку показа | `flutter build apk --release --target-platform android-arm64`, затем установить полученный APK на выбранный телефон |

5. В результате задачи назовите проверенный пользовательский сценарий, выполненные команды, устройство и ограничения. Для камеры и звука приведите измерения и условия опыта. Если проверены только синтетические сигналы, укажите, какая аппаратная проверка ещё нужна. Обновляйте план, когда результаты проверки меняют выбор технологии или объём показа.

Для приёмки релиза пройдите таблицу проверок и трёхминутный сценарий в [плане разработки](docs/MVP_PLAN.md#проверки-перед-презентацией). Сохранение результата после перезапуска и отказ в зачёте при неверном звуке так же важны для демонстрации, как движение кота.
